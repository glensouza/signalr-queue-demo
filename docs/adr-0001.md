# ADR-0001: Real-Time Messaging Topology for DASH 2.0 and Walk-In Queue Management

- **Date:** 2026-07-01
- **Status:** Accepted
- **Deciders:** Glen Souza (Enterprise Cloud Architect), Nathan Sargent
- **Consulted:** Vikrant Salunkhe, Ravi Ganji, Apex Shah, Moueen Shaik, Timothy Meza
- **Confirmed:** 2026-07-09 — SignalR Architecture and Design Review Meeting with Vikrant Salunkhe, Timothy Meza, Moueen Shaik, Apex Shah, and Ravi Ganji. Development team agreed to proceed with Option C as the starting topology; see amendments below.

## Context

DASH 2.0 (internal court portal) and the new Walk-In Queue Management portal need real-time push updates to replace polling: check-ins appearing live for the self-help team, and "Now Servicing" status reaching the public queue display instantly. On 2026-06-26 the development team proposed an implementation using two Azure SignalR Service instances (Standard tier, 1 unit each): `queue-mgmt-signalr-dev` serving anonymous public clients (kiosk check-in and queue display), and `dash-court-signalr-dev` serving the Entra ID-authenticated internal portal behind a private endpoint. The two APIs communicate over REST server-to-server only, share one SQL Server (confirmed 2026-07-09: two separate databases on the same server instance, not schema separation within one database), and use Key Vault with managed identities.

Constraints that shape this decision: all resources must stay in the court Azure tenant; expected concurrent connections are small (kiosks and displays are on-premises devices, plus clerk and self-help staff — likely dozens, not thousands); each Standard unit provides 1,000 concurrent connections at roughly $49 per month; and the court's cost-stewardship obligations apply. The proposal targets .NET 9, which left Microsoft support in May 2026.

## Decision

Keep the public and internal real-time channels logically separated by trust boundary — separate hubs, separate authentication — but do not commit to two Azure SignalR Service instances until two facts are confirmed: (1) whether any client truly connects from the public internet rather than from court networks, and (2) whether either App Service will scale beyond a single instance.

Default position: self-hosted SignalR inside each App Service (**Option C**), at zero additional cost, which is adequate at the expected connection counts. If Azure SignalR Service is adopted, provision two instances only when internet-based clients are confirmed; otherwise a single locked-down instance (or none) suffices.

Independent of topology, the following amendments to the proposal are required: target .NET 10 LTS (not .NET 9, which is out of support); authenticate App Services to SignalR with managed identities only — do not store access-key connection strings in Key Vault; decouple the public check-in path from DASH API availability with retry or queued delivery, so a kiosk check-in does not fail when the internal API is down; enforce schema-scoped SQL logins so the public-facing Queue API cannot read DASH court data; and remove the environment suffix ("-dev") from baked-in resource names in favor of a per-environment naming standard.

**Amendment (2026-07-09):** Confirmed with the development team. Start on Option C. The switch to Azure SignalR Service, if needed, is a single line of code (`AddAzureSignalR` with a connection string) or an app-settings feature flag (e.g. `UseAzureSignalR: true/false`) — no redesign, no code changes to hub logic or the Angular subscription model. If the feature-flag path is used, the Azure SignalR Service resource and connection string must already be provisioned and tested before the flag is flipped in production. Kiosk check-in and the queue display are confirmed as two pages/endpoints (`/kiosk`, `/display`) within a single web application, not separate apps, and will share the same self-hosted SignalR hub under Option C.

**New requirement identified (2026-07-09):** internal staff clients must recover missed messages after a disconnect/reconnect (for example, a staff member stepping away and closing the browser). On reconnect, the client should request a "what did I miss since my last known state" catch-up rather than relying solely on live push. This applies regardless of topology (A, B, or C) and should be designed into the hub protocol from the start, not retrofitted later.

## Alternatives considered

- **Option A — Two Azure SignalR Standard instances (as proposed).** Pros: clean trust-boundary separation; internal instance can sit behind a private endpoint; abuse of the anonymous public hub cannot exhaust internal capacity; each API manages only its own instance, so per-app code is identical to the alternatives. Cons: roughly $100/month for 2,000 concurrent connections against a workload needing perhaps dozens; duplicated operational surface (two managed identities, two network configurations, two resources to monitor); the cost buys capacity, not simplicity.
- **Option B — One Azure SignalR Standard instance with two hubs.** Pros: halves the service cost; one resource to operate; Azure SignalR supports per-hub authorization (anonymous hub alongside an Entra ID hub). Cons: if any client is internet-based the instance cannot be private-endpointed, removing network isolation from internal court-staff traffic; public and internal traffic share one connection quota, so abuse of the anonymous hub degrades the internal portal; couples two applications to one shared resource lifecycle.
- **Option C — Self-hosted SignalR in each App Service (no Azure SignalR Service).** Pros: zero additional cost; simplest operational footprint; entirely adequate for single-instance App Services at the expected connection counts; the hub separation and authentication model are unchanged in code. Cons: scaling an App Service beyond one instance requires adding a backplane or moving to Azure SignalR Service at that point; forgoes managed-service features (connection offloading, built-in scaling).

**Pillar assessment:**

| Well-Architected pillar | Option A — two instances | Option B — one instance | Option C — self-hosted |
|---|---|---|---|
| Cost | ~$100/mo, overprovisioned | ~$49/mo | $0 |
| Security | Best — private endpoint on internal | Weakest — shared public exposure | Good — hubs inherit App Service network posture |
| Reliability | Blast-radius isolation between portals | Shared quota, shared failure domain | Tied to App Service instance health |
| Operational excellence | Two of everything to run | One resource | Nothing extra to run |
| Performance | Far exceeds need | Exceeds need | Sufficient at expected scale |

## Consequences

**What becomes easier:** monthly spend drops to zero (Option C) or is halved (Option B) against the proposal; the operational footprint shrinks; the development team's hub code, event names, and Angular subscription model carry over unchanged from the proposal, whichever topology is chosen.

**What becomes harder:** if either portal later scales out or gains genuine internet clients (for example, phone-based check-in via SMS link), the decision must be revisited and Azure SignalR Service introduced — this is a deliberate, accepted trade: pay for the managed tier when the workload demonstrates the need, not before.

**Follow-up work:** confirm client network locations for kiosk, display, and any future phone check-in (owner: development team); confirm App Service scale-out plans; retarget both APIs to .NET 10 LTS; replace connection-string usage with managed-identity auth to SignalR; add retry or queued delivery to the Queue API → DASH API REST path; define schema-scoped SQL logins; establish per-environment resource naming. Confirmed 2026-07-09: retry policy for check-in/status delivery is retry until success (dead-letter plus a background redrive job if Azure Service Bus is used; a persisted client-side retry, e.g. local storage or IndexedDB, if it is not) — a missed notification must never silently drop, since it means a court visitor never learns it was their turn. Glen Souza to deliver a self-hosted-SignalR POC (with a commented-out line to switch to Azure SignalR) and Azure SignalR emulator documentation by 2026-07-10 (owner: Glen Souza). Glen Souza to prepare and circulate an Azure resource naming-convention proposal, coordinated with Nathan Sargent and Syed, by 2026-07-15, with DASH 2.0 piloting the standard (owner: Glen Souza; Ravi Ganji to coordinate adoption).

**Risks accepted:** self-hosted SignalR ties real-time delivery to App Service instance health; a later migration to Azure SignalR Service is a configuration-level change (`AddAzureSignalR`) rather than a redesign, which is why the risk is acceptable. Missed-message resiliency (see amendment above) is a design risk if not built in from the start — treated as in-scope for the POC, not a later add-on.

**Considered but not actioned (2026-07-09):** Azure Storage (Table Storage in place of SQL Server, Blob Storage — already used by the team's existing Document Management System API — and Storage Queues in place of Service Bus) was discussed as a materially cheaper alternative for this workload. Not actioned for DASH 2.0 because the SQL tables and APIs are already built and the conversion effort is not justified mid-flight; recommended as the default starting point for future low-complexity projects. **This POC demonstrates that path anyway** — see the main [README](../README.md) for how Table Storage and Blob Storage are wired in as a swappable persistence provider.
